## Authentication proposal

Use the school's existing Google Workspace account through Supabase Auth's standard Google OAuth provider, **PKCE S256**, identity scopes `openid email profile`, and an account chooser. No Gmail, Drive, contacts, calendar, offline Google access/refresh token, One Tap script, marketing list or teacher access. Account identity is the verified Supabase `user.id`, never a name, email, typed school domain or editable metadata. A Google domain hint is not authorization; school restrictions belong in school/admin consent configuration.

Basic OAuth can send provider display name/avatar metadata to Supabase Auth in addition to email. The app does not need or fetch an avatar or make a public profile. Review this collection with the school; do not claim OAuth collects only a UUID. Provider secrets stay only in Supabase's provider settings, never Pages. Standard Google OAuth is distinct from paid enterprise SAML SSO. [Official Google setup](https://supabase.com/docs/guides/auth/social-login/auth-google), [PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow).

The prepared adapter keeps the SDK session in memory. Its custom storage forwards only the SDK's exact `-code-verifier` key to sessionStorage across a full redirect. Session tokens never enter sessionStorage/localStorage. Provider tokens are stripped from the stored memory representation. `detectSessionInUrl:false` permits deliberate code exchange and URL cleanup before private rendering. A failed exchange clears verifier/session data and leaves the existing local app untouched. A real callback still needs a tested account/device flow in B2–B4. Recreate the foundation after sign-out when composing a new account context.

Before any redirect, the future caller must show the privacy notice and preserve/export pending memory work or allow cancellation. The two explicit booleans in this low-level helper represent caller preconditions, not a finished consent or recovery UI. Shared-mode loss warnings, inactivity lock, protected-profile durable storage, cross-tab SDK Auth events, account switching/generation guards on every data callback and deletion flows remain B2–B4 work. The SDK's same-origin Auth event channel is not a confidentiality boundary. App logout does not log the student out of Google. Returned logout status distinguishes server revocation failure; existing JWTs also require the server session check. [Session behavior](https://supabase.com/docs/guides/auth/sessions).

A handwritten SQL copy would create a second semantic authority and require paired schema changes. PostgreSQL `json` avoids jsonb normalization of arbitrary unknown values. Full schema parity has **not** been established or implemented.

**Recommendation, awaiting explicit owner approval for student use:** server acceptance means privately stored, authorized, versioned and resource-bounded data; it does **not** certify a valid H4 backup. Require canonical `parseSavedState` plus `serializeBackup` before upload and before any remote head/history/restore adoption. The new pure inspector returns raw text and observed revision as quarantine on failure. It never replaces valid local progress. B3 must persist that quarantine safely, pause automatic adoption/upload, provide a labelled raw recovery download and require explicit CAS repair. A quarantine raw file is not promised to be a restorable backup.

| Fixture group | Proposed server | Canonical client |
| --- | --- | --- |
| Migrated V4–V8, safe unknown fields, escaped Unicode, lone surrogate in unknown text, exact 2MiB multibyte/escaped text | Accept, preserve exact bytes; **server round trip unverified** | Candidate + exportable backup; passed |
| Malformed JSON, array root, string/future version, missing/wrong goals type, >1,000 goals, >2MiB | Reject before head/receipt change; **unverified** | Quarantine; passed |

The integration suite intentionally fails if a supposedly compatible Unicode/number/maximum-size input fails the real server. Do not remove an unknown field, reduce the existing backup limit, or rewrite fixture expectations to disguise a parser/transport mismatch. Escaped request bodies can exceed 2MiB even when stored text is exactly 2MiB. Those round trips and runtime measurements are blockers for release. Ordinary text containing `<img ...>` is inert data, not executable HTML; validation is not an HTML sanitizer and future rendering must continue using escaped/text content.

## Resource and retention proposal

Proposed limits: 2MiB text; safe integer revisions; 30 committed new requests/minute; 500/day; 2,000 retained receipts/account; ten unresolved conflicts; 16MiB retained payload bytes/account including the current head. Exact retries return their original receipt before new-request quotas. The extra 2,000-receipt ceiling bounds metadata beyond the architecture's payload cap; it can stop a heavy writer early and needs owner approval. Errors do not acknowledge local work.

The write transaction compacts accepted payloads to the latest three while retaining receipt hashes/outcomes. It never compacts unresolved conflicts. Operator maintenance proposes 30-day receipt retention and seven days for resolved-conflict payloads, under the same owner advisory lock. No conflict-resolution endpoint exists yet. Maintenance failure retains data and may block new writes; it does not silently evict unresolved work. Expired receipts plus stale bases can produce another conflict, never replay an XP delta. Revisions/outcomes are assigned on the server; XP remains self-reported content, not a server-certified achievement.

The migration proposes a five-second authenticated-role timeout and explicitly reloads PostgREST configuration. This affects that role across the **dedicated test project**, so review it before applying. It must be verified through an actual REST timeout probe, not `SET ROLE` or a function-local setting alone. [Official timeout configuration](https://supabase.com/docs/guides/database/postgres/timeouts).

**Resource limitation:** transaction quotas count successful committed requests; rejected/malformed/rolled-back requests do not leave rate counters. This is not a general API abuse limiter. Gateway body limits, effective timeouts, repeated hostile input cost, per-account concurrency and project-wide Free headroom are still unmeasured. Do not promise that client validation prevents an attacker from submitting invalid own-account data. No public student rollout until those tests and the architecture's operator pause/backup gates pass. No paid rate service, scheduler or automatic upgrade is assumed.
